# poe-alarm-clip-only

第二次尝试。纯剪贴板识别，**全程不读屏幕**。

上一版（`clipboard-lab` 分支，已删）用屏幕指纹判断"石头砸下去了没"，为此拖进来截取区域、蓝字掩膜、容差阈值三样东西——三样都要配、三样都会出问题。而那一整串复杂度，只是为了省一次剪贴板往返。

这版把它全删了。

---

## 变化检测就是一行

```rust
if 这次读到的文本 != 上次读到的文本 { 就是新 roll }
```

文本本身既回答了"变了没"，也**就是**词缀列表。所以：

- 不需要选区域
- 不需要蓝字掩膜
- 不需要指纹
- 不需要容差阈值
- 不需要校准
- 提示框背后的场景怎么动都无所谓

代价：服务器还没裁定完的时候，得多发几次 Ctrl+C。**这个代价有多大，就是这个程序要测的唯一问题。**

## 和上一版比少了什么

| | 上一版 | 这一版 |
| --- | --- | --- |
| 依赖 `poe-alarm-vision` | 是 | **否** |
| 需要截取区域 | 是（没有就报错退出） | **否** |
| 需要校准 | 是 | **否** |
| 可调参数 | 区域 + 掩膜 + 阈值 | 无（只有超时） |
| 失败模式 | 抓帧失败/指纹乱跳/阈值不对/区域太大 | 剪贴板超时 |

保留的：`poe-alarm-core` 规则引擎、你保存的规则、先拦截后放行、全部 fail-closed、钩子诊断。

## 跑法

```bash
cargo build --manifest-path rust\Cargo.toml --release -p poe-alarm-clip-only
```

**终端要以管理员身份运行**（游戏是管理员权限的话，低级鼠标钩子装得上但收不到任何事件）。

```bash
rust\target\release\clip-only-lab.exe
```

然后：

1. 切到游戏，进藏身处
2. 确认终端里出现 `[armed] game focused`
3. 动一动鼠标，3 秒后应该看到 `[watching] events 数字在涨`
   - 如果反复出现 `hook saw 0 mouse events`，就是**权限问题**，用管理员开终端
4. 光标悬停在要砸的蓝装上，右键拿起改造石，正常砸

每砸一次打印一行：

```
  #12   copies 2   first 34.1ms   verdict 78.5ms   miss  (2 lines)
```

- `copies` —— 这次花了几次 Ctrl+C 才等到新文本。**这是这版方案的核心代价指标。**
- `first` —— 第一次往返耗时
- `verdict` —— **点击到判定完成的总时间。这个数直接和你 OCR 的 120-150ms 比。**

`Ctrl+Shift+F12` 解锁，`Ctrl+Shift+F9` 退出并出报告。

## 报告怎么看

退出后会打印：

- `click -> verdict` 的 p50/p90/p95/p99
- **每 roll 用了几次 Ctrl+C 的分布**
- `decided within 60/80/100/120/150ms` 各占多少
- 一句结论

判读：

| 结果 | 含义 |
| --- | --- |
| 120ms 内 ≥ 99% | 至少和 OCR 一样快，而且没有区域没有模型 → **可以扔掉 OCR** |
| 120ms 内 ≥ 90% | 接近，配合先拦截后放行，慢的那几次只是顿一下不是漏判 |
| 120ms 内 < 90% | 多余的往返太贵，试 `--first-delay-ms` 或者留着 OCR |
| fail-closed 超过 5% | **先修这个再看延迟**，一个老在放弃的快管线不叫快 |

## 可调参数

```
--budget-ms N        对标的 OCR 延迟，默认 120
--first-delay-ms N   第一次 Ctrl+C 之前先等一下，默认 0
--poll-gap-ms N      两次 Ctrl+C 之间的间隔，默认 0
--copy-timeout-ms N  单次往返超时，默认 600
--deadline-ms N      从点击算起的总超时，默认 1500
```

如果报告显示 `copies` 大多是 2 次，说明第一次几乎总是白发的（服务器还没回包）。这时候 `--first-delay-ms 30` 之类的值可能让 `copies` 降到 1，总延迟反而下降。**这是这版唯一值得调的参数，而且调它有明确的数据依据。**

## 已知代价

1. **会向游戏发按键。** 正式版 README 那句 "never synthesizes or replays any input into the game" 在这里不成立。合规没问题（GGG 加 Ctrl+C 就是给工具用的），但**要合并的话那句话必须改**。
2. **每 roll 覆盖一次剪贴板。** 这版无法避免——剪贴板就是数据通道本身。
3. **光标必须停在装备上。** 挪开会读到别的东西或读不到，目前 fail-closed 兜住，没做坐标校验。
4. **先拦截后放行改变手感。** 慢了是顿一下，不是漏判。

## 实测结论（已完成）

### 最终数字

| 指标 | 实测 |
| --- | --- |
| 剪贴板往返 | p50 **3ms**，p99 9.5ms |
| 词缀解析准确率 | **100%**，繁中实机验证 |
| 检测延迟 `detection staleness` | p50 **26.8ms**，p90 51.0ms，p95 54.2ms |
| 实战可承受点击速度 | **80ms 稳中**，50ms 临界（OCR 版需要 150ms） |
| 需要截取区域 / OCR 模型 / 校准 | **都不需要** |

样本：199 rolls，16 hits，1560 次轮询。

### 检测延迟是旋钮，不是极限

`per-copy timeout` 直接决定检测延迟，三点对照：

| 超时 | staleness p50 |
| --- | --- |
| 600ms | 632.4ms |
| 60ms | 80.9ms |
| 25ms | **26.8ms** |

机制：**改造进行中客户端拒绝答复 Ctrl+C，它重新开口的那一刻就是新词缀出现的时刻。** 所以超时设多长，就有多长时间是瞎的。现在 26.8ms 已由轮询间隔（15ms）主导，继续压超时收益递减。

### 被推翻的假设（全部是作者的）

- ❌ 「剪贴板往返 30~60ms」→ 实测 3ms，错一个数量级
- ❌ 「先拦截后放行只是顿一下」→ 实测 2.9 次点击才砸上一个，不可用
- ❌ 「改造要 220ms，是服务器硬延迟」→ 大部分是 600ms 超时造成的
- ❌ 「识别方式和拦截策略要绑在一起」→ 完全正交，绑死是最大的设计错误
- ❌ 「p50 6.8ms 说明很快」→ 基准过期造成的假象，实际慢了一拍

### 还没解决的

1. `copy failures` 约 14%（改造期间客户端拒答，**属正常现象**，每次代价已降到 25ms）
2. 每 roll 覆盖剪贴板，无法避免
3. 需要管理员权限（游戏是管理员权限时，低完整性钩子收不到输入）
4. 会向游戏发按键 → 正式版 README 那句 *"never synthesizes or replays any input into the game"* **必须改**
5. 光标必须停在装备上，未做坐标校验
