# poe-alarm-clip-only

第二次尝试。纯剪贴板识别，**全程不读屏幕**。

上一版（`clipboard-lab` 分支，已删）用屏幕指纹判断"石头砸下去了没"，为此拖进来截取区域、蓝字掩膜、容差阈值三样东西——三样都要配、三样都会出问题。而那一整串复杂度，只是为了省一次剪贴板往返。

这版把它全删了。

---

## 变化检测就是一行

```rust
if 这次读到的文本 != 上次读到的文本 { 就是新 roll }
```

文本本身既回答了"变了没"，也**就是**词缀列表。所以：

- 不需要选区域
- 不需要蓝字掩膜
- 不需要指纹
- 不需要容差阈值
- 不需要校准
- 提示框背后的场景怎么动都无所谓

代价：服务器还没裁定完的时候，得多发几次 Ctrl+C。**这个代价有多大，就是这个程序要测的唯一问题。**

## 和上一版比少了什么

| | 上一版 | 这一版 |
| --- | --- | --- |
| 依赖 `poe-alarm-vision` | 是 | **否** |
| 需要截取区域 | 是（没有就报错退出） | **否** |
| 需要校准 | 是 | **否** |
| 可调参数 | 区域 + 掩膜 + 阈值 | 无（只有超时） |
| 失败模式 | 抓帧失败/指纹乱跳/阈值不对/区域太大 | 剪贴板超时 |

保留的：`poe-alarm-core` 规则引擎、你保存的规则、全部 fail-closed、钩子诊断。

**拦截策略和识别方式是正交的**，早期版本把两者绑死是最大的设计错误。默认已改为 `detect-then-block`（点击自由通过，只有命中才锁），和正式版 OCR 一致。

## 跑法

```bash
cargo build --manifest-path rust\Cargo.toml --release -p poe-alarm-clip-only
```

**终端要以管理员身份运行**（游戏是管理员权限的话，低级鼠标钩子装得上但收不到任何事件）。

```bash
rust\target\release\clip-only-lab.exe
```

然后：

1. 切到游戏，进藏身处
2. 确认终端里出现 `[armed] game focused`
3. 动一动鼠标，3 秒后应该看到 `[watching] events 数字在涨`
   - 如果反复出现 `hook saw 0 mouse events`，就是**权限问题**，用管理员开终端
4. 光标悬停在要砸的蓝装上，右键拿起改造石，正常砸

每检测到一个新 roll 打印一行：

```
  roll 42   seen 82.7ms   HIT   (2 lines)
```

`Ctrl+Shift+F12` 解锁，`Ctrl+Shift+F9` 退出并出报告。

## 报告怎么看

**只看 `detection staleness`。** 它是"上一次轮询没看到、这一次看到了"之间的窗口——roll 一定在这个窗口内出现，所以警报最多迟这么多。**这是唯一只取决于本工具、不取决于你点多快的数。**

`click -> detected` 从你最近一次点击起算，你点得越快它越小，**没有参考价值**，报告里保留只为对照。

判读：staleness 的 p90 要小于你的点击间隔，否则会点过头。实测 p90 51ms → 80ms 点击间隔稳中，50ms 临界。

## 可调参数

```
--watch-interval-ms N   轮询间隔，默认 15（现在的主要瓶颈）
--copy-timeout-ms N     单次复制超时，默认 25（直接决定检测延迟）
--observe               只测量不拦截：每次点击两次复制，扫出改造耗时曲线
--test-copy N           只测 Ctrl+C 通不通，不装钩子不跑规则
--scancode              改用硬件扫描码发按键
--block-first           旧策略：每次点击都等判定（实测 2.9 次点击才砸上一个，不推荐）
--watch-interval-ms 8   想再压延迟可以试，收益递减且剪贴板churn变多
```

## 已知代价

1. **会向游戏发按键。** 正式版 README 那句 "never synthesizes or replays any input into the game" 在这里不成立。合规没问题（GGG 加 Ctrl+C 就是给工具用的），但**要合并的话那句话必须改**。
2. **每 roll 覆盖一次剪贴板。** 这版无法避免——剪贴板就是数据通道本身。
3. **光标必须停在装备上。** 挪开会读到别的东西或读不到，目前 fail-closed 兜住，没做坐标校验。
4. **需要管理员权限。** 游戏以管理员运行时，低完整性进程的低级鼠标钩子收不到任何输入。

## 不要了

```bash
git checkout main && git branch -D clip-only-lab
```

生产代码零改动。

## 实测结论（已完成）

### 最终数字

| 指标 | 实测 |
| --- | --- |
| 剪贴板往返 | p50 **3ms**，p99 9.5ms |
| 词缀解析准确率 | **100%**，繁中实机验证 |
| 检测延迟 `detection staleness` | p50 **26.8ms**，p90 51.0ms，p95 54.2ms |
| 实战可承受点击速度 | **80ms 稳中**，50ms 临界（OCR 版需要 150ms） |
| 需要截取区域 / OCR 模型 / 校准 | **都不需要** |

样本：199 rolls，16 hits，1560 次轮询。

### 检测延迟是旋钮，不是极限

`per-copy timeout` 直接决定检测延迟，三点对照：

| 超时 | staleness p50 |
| --- | --- |
| 600ms | 632.4ms |
| 60ms | 80.9ms |
| 25ms | **26.8ms** |

机制：**改造进行中客户端拒绝答复 Ctrl+C，它重新开口的那一刻就是新词缀出现的时刻。** 所以超时设多长，就有多长时间是瞎的。现在 26.8ms 已由轮询间隔（15ms）主导，继续压超时收益递减。

### 被推翻的假设（全部是作者的）

- ❌ 「剪贴板往返 30~60ms」→ 实测 3ms，错一个数量级
- ❌ 「先拦截后放行只是顿一下」→ 实测 2.9 次点击才砸上一个，不可用
- ❌ 「改造要 220ms，是服务器硬延迟」→ 大部分是 600ms 超时造成的
- ❌ 「识别方式和拦截策略要绑在一起」→ 完全正交，绑死是最大的设计错误
- ❌ 「p50 6.8ms 说明很快」→ 基准过期造成的假象，实际慢了一拍

### 还没解决的

1. `copy failures` 约 14%（改造期间客户端拒答，**属正常现象**，每次代价已降到 25ms）
2. 每 roll 覆盖剪贴板，无法避免
3. **会向游戏注入按键，这一条同时带来两个代价**（早前当成两条独立的记，是错的）：

   - 正式版 README 那句 *"never synthesizes or replays any input into the game"* **必须改**
   - **游戏以管理员权限运行时，本程序也必须是管理员**

   这两件事是同一件事。UIPI 禁止中完整性进程向高完整性窗口注入输入，所以
   注入这个动作既破坏了那句声明，也破坏了"零权限即可运行"。

   正式版之所以不需要权限，正是因为它一次都没越过这条线：

   | 操作 | 机制 | 受 UIPI 限制 |
   | --- | --- | --- |
   | 识别 | `BitBlt` 抓桌面像素 | 否 |
   | 拦截 | 分层置顶窗口占住像素 | 否（点击落在自己的窗口上） |
   | 钩子 | 仅在警报交接时接管待处理点击 | 否（目标是自己的覆盖窗口） |

   **已确证。** 干净对照：同一条命令、同一流程，只有权限不同。

   | 终端 | `--test-copy 20` |
   | --- | --- |
   | 管理员 | **20/20 成功**，往返 p50 3.9ms |
   | 普通 | **0/20**，全部在 25ms 处超时 |

   超时意味着剪贴板序列号从未变化，即客户端根本没收到按键。AutoHotkey 官方
   FAQ 记录的是同一件事：要给管理员权限的程序发按键，AHK 自身必须以管理员
   运行。

   那个同样注入按键的 aardio 工具（`自动改造石v1.182`）manifest 是
   `asInvoker`，**它没有解决这个问题，只是没声明**——它的用户要么游戏本来就
   不是管理员，要么自己摸索出右键以管理员运行。

   **条件性**：普通启动的 POE 是中完整性，不需要任何提权。只有游戏被以管理员
   权限拉起时才成立（例如加速器需要管理员，游戏作为子进程继承提权）。

   `--no-hook` 去掉了钩子，但去不掉这条——注入本身就需要权限对等。程序现在会
   在游戏获得焦点时主动探测（读不到对方进程令牌 = 对方权限更高）并提示，而不是
   让用户撞一墙超时才发现。

5. 光标必须停在装备上，未做坐标校验

## 关于管理员权限

### 什么时候需要

**只在游戏本身以管理员权限运行时。** 普通启动的 POE 是中完整性进程，本程序
普通权限即可，全程不需要任何提权。

游戏会变成管理员权限，通常是被一个管理员权限的父进程拉起来的——最常见的是
**加速器**（要装网络驱动，自身需要管理员），游戏作为子进程继承了提权。

### 为什么需要

本程序必须向游戏**注入** Ctrl+C 才能拿到物品文本。Windows 的 UIPI 禁止中完整性
进程向高完整性窗口注入输入，所以权限不对等时按键根本到不了游戏。

实测：`--test-copy 20` 管理员终端 20/20，普通终端 0/20 全部超时。

这不是本程序独有的限制。AutoHotkey 官方 FAQ 记录同一件事；查价器、罗技驱动的
鼠标宏遇到管理员权限的游戏时也一样。

### 为什么不用 manifest 强制要求管理员

因为那会让**所有人**都过一次 UAC，包括大多数根本不需要提权的用户，白白丢掉
"零权限即可运行"这个属性。

本程序的做法是：**默认普通权限启动，只在检测到权限不匹配时才提示。**

检测方式：中完整性进程读不到管理员进程的令牌，所以"能读自己的令牌、读不到前台
进程的令牌"就唯一地指向这个情况。见 `clipboard.rs` 的
`foreground_process_outranks_us()`。

需要时加一个参数即可，会弹一次 UAC 并在新窗口继续：

```bash
rust	argetelease\clip-only-lab.exe --elevate
```

（正式版如果合并这条路，对应的应该是界面上一个「以管理员身份重启」按钮，
而不是命令行参数。）

### 提权之后到底用来做什么

**只有一件事：让 `SendInput` 发出的 Ctrl+C 能到达游戏窗口。**

除此之外没有任何需要提权的操作——不读游戏内存、不注入 DLL、不改注册表、不写
系统目录、不联网。要核对的话看这三处就够：

| 位置 | 用途 |
| --- | --- |
| `clipboard.rs` → `send_ctrl_c()` | 唯一的输入注入点 |
| `clipboard.rs` → `relaunch_elevated()` | 唯一的提权点，`ShellExecuteW` + `runas` |
| `clipboard.rs` → `read_text()` | 只读剪贴板，不需要提权 |

`grep -rn "SendInput\|ShellExecuteW\|OpenProcess" rust/crates/poe-alarm-clip-only/src`
能列全所有相关调用。
