# 高端装备复合规则真实语料验证

验证日期：2026-08-13

## 结论

现有规则引擎能够表达并正确计算当前讨论的高端装备制作场景：

- 多个“值得停手的结果”之间为任选其一；
- 每组结果可以要求全部命中或至少命中指定数量；
- 可表达“4 个候选词缀至少命中 2 个”；
- 每个数值位置能独立设置闭区间、下限或精确值；
- 同一条实际词缀不能因文字重叠或分两行显示而重复计数；
- 全域与法术、攻击技能与近战技能等相近词缀仍会严格区分。

这项验证回答的是：给定正确的识别文字时，规则引擎能否得出正确结果。分两行显示的复合词缀案例还会经过与正式监控相同的行身份整理，验证同一条词缀不会跨行重复计数。

语料探针不会实际运行文字识别模型，因此不能证明所有分辨率、语言和文字颜色都已识别正确。识别能力仍需通过截图回放和实机测试验证。

这份语料只验证停手规则，不提供鼠标点击保护。曾经试做的谨慎模式因流程未闭环、实机出现卡死且未能可靠拦截点击，已经从 1.0 移除。高端装备语料继续保留，是因为它仍能检验单词缀和多词缀组合的判断正确性，与是否存在谨慎模式无关。

## 数据与复现

可复现语料：

- `tests/fixtures/mirror-tier-composite-rules.json`

无需第三方测试框架的探针：

- `tests/PoeAlarm.MirrorCorpusProbe`

运行：

```powershell
dotnet run --project tests\PoeAlarm.MirrorCorpusProbe\PoeAlarm.MirrorCorpusProbe.csproj -c Release --no-build
```

当前语料包含 14 条来源记录、7 个规则场景、36 个断言案例；其中 POE1 三个、POE2 三个场景来自官网交易论坛的实际高端成品，另一个 POE1 珠宝场景来自当前 PoEDB 词缀池，用于覆盖用户提出的“四选二”玩法。每个来源在语料文件中保存网址、访问日期、游戏、装备槽和证明内容。

案例覆盖：

- 15 个正例；
- 21 个负例；
- 7 个相近词缀负例；
- 8 个少一条负例；
- 13 个数值边界案例；
- 2 个直接使用普通装备提示框显示值的真实高端装备正例；
- 1 个“同一条复合词缀不能重复计数”的跨层身份案例。

## 对当前制作场景的适用性

### 可以直接应用

“命中任一可接受结果便报警”和“4 条里至少中 2 条”都能直接应用。比如同一套珠宝规则可以把：

1. 全域暴击率；
2. 法术暴击率；
3. 法术暴击加成；
4. 攻击速度；

设成“至少命中 2 条”，并再加一组“必须全部命中”的法术暴击组合。若多组结果同时成立，程序按配置顺序选择第一组作为主要命中结果，同时保留其他已成立结果的判断记录。

武器的阶段性制作也能表达：一组结果监视前缀组合（纯物理 + 复合物理 + 点伤），另一组结果监视后缀或完工条件（攻速 + 技能等级）。数值边界均按屏幕当前显示值判断。

### 必须明确的限制

1. **无法判断破裂来源。** 普通装备提示框只改变文字颜色，不显示“破裂”字样。程序可以判断一条可见词缀和值是否存在，但不能承诺它就是破裂词缀。语料因此只记录破裂或亵渎来源，不把来源本身作为停手条件。
2. **同一条复合词缀不能拆开凑数。** 例如，“增加 78% 物理伤害”和“+192 命中值”来自同一条分两行显示的词缀时，它只能贡献一次命中。专门负例验证了保留行身份时不会重复计数。这里证明的是识别结果交给规则引擎后的去重，不是实机文字识别精度。
3. **品质、催化剂、符文和附魔可能改变显示值。** 当前规则比较最终显示值，无法反推出未经这些效果修正的基础值或词缀等级。界面会提醒用户按最终显示值配置。
4. **普通装备提示框无法可靠说明前缀、后缀、词缀等级和原有词缀身份。** 1.0 不承诺根据这些不可见信息进行判断，也不提供“原有词缀消失时拦截点击”的保护功能。

## 与未来保护功能的关系

这份语料能继续用于验证未来方案中的“目标结果是否命中”，但不能证明点击拦截、画面变化确认或异常恢复是否安全。类似保护功能若重新设计，必须先明确完整使用流程，再单独通过真实点击节奏、停止程序、识别失败和异常退出等实机测试。

在这些问题得到闭环验证前，高端装备语料只作为规则正确性测试，不构成任何点击保护承诺。
