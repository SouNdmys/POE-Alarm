# Rust 原生预览版验收报告（2026-08-13）

## 结论

当前候选版只能继续作为 **Rust 预览版**，不能替代或下架 `.NET 1.0.0`。

已经实测通过的重点包括：像素热路径、真实截图准确率、用户 `3.73%` 数值边界、
480 次真实像素瞬态回放、1,000 次运行时启动/停止、500 次截图意图替换/取消、
500 次界面自测、全 Paddle 繁中兼容路径、原生界面行为对齐、高 DPI 自适应、启动速度、
空闲内存和发行体积。

繁中延迟已经从早期落后于 `.NET` 优化到同档或更快：POE2 繁中 Rust warm p50/p95
为 `31.0343/47.8532 ms`，同机 `.NET` 为 `31.8/50.0 ms`；POE1 8.11 繁中 Rust
为 `36.3542/57.2188 ms`，`.NET` 为 `40.1/61.1 ms`。但 POE2 p50 只快约 `2.4%`，
POE1 p50 只快约 `9.3%`，仍没有达到验收合同中“p50 至少快 10%”的理想门槛。
这项结果只能说明 Rust 已追平现有体验，不能单独支持正式切换。2 小时真实游戏监控、
四种配置各 30 分钟实机制作、POE1 English 私有截图清单、真实两行瞬态和真正的干净
Windows 验收也仍未完成，因此当前版本继续标为 Preview。

## 1. 像素筛选、指纹与裁剪

同一合成 `1433×1117` BGRA 输入，先 `.NET → Rust`，再交换为 `Rust → .NET`；
每轮预热 200 次、采样 3,000 次，两轮合计每端 6,000 个样本。两端语义指纹均为
`CEC2A8DDB1A49BCB`。

| 流程 | .NET p50 / p95 | Rust p50 / p95 | Rust 差异 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 指纹 / mask + 指纹 | `1.222 / 1.382 ms` | `0.696 / 1.168 ms` | 快 `43.0% / 15.5%` | 通过 |
| mask + 指纹 + 分行 + BGRA 裁剪 | `1.860 / 2.062 ms` | `1.293 / 1.842 ms` | 快 `30.5% / 10.7%` | 通过 |

## 2. 真实截图准确率与延迟

POE2 English、POE2 繁中和 POE1 8.11 繁中清单均在独立进程中重复五轮。Rust Quick
的 warm 统计排除每个进程的第一条 cold 样本；`.NET` 汇总直接来自五轮逐目标
`decision` 样本。旧繁中 Rust 最终值只来自一轮，表中已明确标注，不能与五进程样本
混算。

| 清单 | Rust 五轮准确率 | .NET 五轮准确率 | .NET p50 / p95 | Rust warm p50 / p95 | 性能门槛 |
| --- | ---: | ---: | ---: | ---: | --- |
| POE2 English Quick | `190/190` | `190/190` | `3.7 / 64.8 ms` | `1.947 / 39.717 ms` | 通过 |
| POE2 繁中 Quick | `190/190` | `190/190` | `31.8 / 50.0 ms` | `31.0343 / 47.8532 ms` | 追平并略快；p50 未达快 10% |
| POE1 8.11 繁中 Quick | `135/135` | `135/135` | `40.1 / 61.1 ms` | `36.3542 / 57.2188 ms` | p50 快约 9.3%；未达快 10% |
| POE1 旧繁中 Quick | `26/26`（单轮） | `130/130`（五轮） | 每轮 p50 `63.0–70.8 ms`，p95 `81.4–93.2 ms` | `66.176 / 83.869 ms` | 单轮同档；不得写成五进程结果 |

结构化模式另跑五轮：POE2 English `190/190`，且 primary 与独立 confirmation 都为
`190/190`；POE2 繁中 `190/190`；POE1 8.11 繁中 `135/135`。POE2 English
结构化 warm 总耗时 p50/p95 为 `75.700/139.287 ms`，其中 primary 为
`38.804/80.196 ms`，confirmation 为 `36.463/54.021 ms`。其他三条路径在这些
样本中未触发 confirmation，不能据此填写 confirmation 延迟。

旧繁中 JSON 是逐物理行 Quick 清单。将同一张图的 7、9 或 10 条逐行目标同时当成
必须全部恢复的压力测试时，生产 Structured 为 `14/26`，而同轮直接物理行验证为
`26/26`、错行报警 0。它不代表产品把跨图 26 条目标拼成一组。为验证真实多词缀规则，
另使用每张 4–6 条真实词缀的三张 tooltip，分别组装 2/4/10/20 条条件，不足部分由
跨图严格反例补齐；POE1 繁中、POE2 English、POE2 繁中各跑 60 轮，全部正例命中且
反例误报 0。生产源码的本地恢复预算仍为最多 2 个 work unit。

POE1 English 的原始图片清单在当前仓库和本机历史截图树中均不存在，因此本轮没有用
POE2 English 图片冒充该证据；此项保持 pending。

补充审计还检查了本机另一个 POE1 项目的 English fixtures：那里确有真实 POE1
English 截图，但内容是游戏内通货交易所、订单表格和市场字段，不是 POE Alarm 的装备

`semantic-neighbor` 与 `cross-screenshot` 负例，并提供 `--require-negative-contract` 发布
合同；采集要求和 Quick/Structured 命令见
`rust/crates/poe-alarm-recognition/POE1_ENGLISH_PRIVATE_GATE.md`。由于缺少适用的真实图片，
本轮只验证了门禁合同本身，未将 schema fixture 写成识别通过。

最终五进程繁中样本位于忽略提交的
`rust/target/recognition-evidence/zh-latency-final/`，汇总文件为 `aggregate.csv`；旧版

## 3. 用户 3.73% 暴击率实图

对用户提供的 `1433×1117` POE2 繁中截图执行生产 Structured 识别，模板为
`+(3.11—3.8)%暴擊率`。识别行包含 `+ 3.73 % 暴 擊 率`：

- “至少 3.1”：文字命中，数值条件为 `true`；
- “至少 3.8”：文字仍命中，数值条件为 `false`。

两次运行的 OCR 为 `71.675 ms` 与 `67.450 ms`。原始文件：
`recognition/user-3.73-min-3.1.log`、`user-3.73-min-3.8.log`。

## 4. ONNX、全 Paddle 兼容路径与规则热路径

五个独立进程执行官方模型、字典哈希、形状和真实全零推理自检：

- 会话创建 `95.722–100.477 ms`；
- 首次推理 `7.462–8.082 ms`；
- 包含资产读取与校验的总耗时 `119.380–124.637 ms`。

绝对值低于 `240 ms` 门槛。20 条规则 Release warm 探针为
`149.440 µs/evaluation`（20,000 次），低于 `0.25 ms` 目标。

当系统没有可用的 Windows 繁中 OCR 语言时，生产识别器现在会进入完整的 Paddle
兼容路径，而不是只提供局部补识别：Quick 与 Structured 都会按物理行渐进处理，并以
每轮最多 2 个工作单元推进严格分段恢复。繁中 Paddle 蓝字掩膜保持 `.NET 1.0` 的
`minimum blue = 100`、`minimum dominance = 14`、暖色通道差上限 `72`；私有旧繁中
物理行门禁为 `26/26`，错行报警 0。生产启动仍要求 ONNX Runtime、模型和字典三项资产
齐全，缺失时明确失败，不会静默降级成宽松匹配。

## 5. 真实像素瞬态回放

独立诊断探针从真实截图目标 band 派生“目标出现/消失”帧，直接驱动 Rust 生产
`ProductionRecognizer` 与 `Monitor`。点击模型只在输入保护未持有时改变帧；被吞掉的
点击不补发、不重放。四条路线为普通 top-1、长词缀、CTC-assisted 和调度 rank-3。

| 规模 | hit / timely | overroll | captured miss | false alert |
| --- | ---: | ---: | ---: | ---: |
| 4 路线 × 6 档 × 20 次 = 480 | `480/480` | `0` | `0` | `0` |

六档为 `30/40/50/60/80/100 ms`。最慢路线的 onset→decision p95 约
`123 ms`；保护事件在其完成前吞掉后续点击，所以仍无点过头。此探针验证 Rust 监控事件
与生产 OCR 的组合，不等同于真人鼠标驱动或 2 小时游戏实机 soak。

本轮 `weapon-shrine-on-kill` 使用真实长词缀原始行，没有像 .NET 专项探针那样把像素
重排成两个物理行；因此“真实像素两行换行瞬态”仍需另补，不能由这 480 次结果代替。

2026-08-13 又对当前私有截图树做了有界素材审计：共检查 `25` 张原图和 `8` 份清单，
以生产 Quick OCR 的严格匹配证据逐目标统计，得到 `125` 个 strict match，
`physical_line_count=1` 为 `125` 个，`physical_line_count=2` 为 `0` 个。两个肉眼最像
候选的 POE1 长词缀——`weapon-shrine-on-kill` 与 `true-guard-explode-on-kill`——在游戏
原图本身也是单行；前者命中依赖目标辅助证据，后者当前 OCR 同样没有形成跨两行严格
证据。POE2 中英文完整清单的严格命中也全部是单行。旧 `.NET --wrap-case` 会把真实字形
像素人工重排成相邻两行，虽然没有渲染假字，但仍不是游戏自然排版，因此本次没有拿它
冒充真实两行门禁。

审计原始 CSV、日志及原图 SHA-256 索引位于忽略提交的
`transient/natural-two-line-audit/`。由于当前素材集中不存在合格输入，六档回放本轮没有
执行，也没有生成虚假的 hit/timely 统计。补齐门禁所需的新素材必须是游戏原生 tooltip：
同一条目标词缀肉眼占相邻两行，完整 tooltip 和所选 ROI 均保留，且生产预检必须返回
strict `physical_line_count=2`；然后才能按既定 `30/40/50/60/80/100 ms × 20` 运行。

逐目标审计使用 `recognition-manifest-probe --mode quick --show-physical-matches
--physical-match-csv <ignored.csv> --audit-physical-matches`。最后一个开关只跳过旧清单的
“图片名必须唯一”和逐 band Paddle 复核，以便盘点重复 ROI；它不改变生产 OCR、matcher
或匹配结果。进程退出码仍会暴露普通清单回归失败，物理行 CSV 只写 strict evidence，
所以“125 个严格证据均为一行”不把辅助命中误记为严格两行。

原始文件：`transient/rust-guarded-real-pixel.csv`、
`transient/rust-guarded-summary.csv`。

## 6. 生命周期与界面进程

- Runtime actor 1,000 次 start/stop：`15.58 s`，识别器峰值 1、结束存活 0，保护代际
  清空，无迟到命中/截图/故障，最终 shutdown 小于 1 秒。
- 500 个截图替换/取消意图：`0.16 s`，只保留一个在途识别和最新意图，识别器峰值 1，
  每个被替换请求恰好一次取消，无迟到结果，最终 shutdown 小于 1 秒。该测试使用可控
  后端验证 actor 所有权，不宣称执行了 500 次真实 WIC + ONNX 解码。
- 原生 UI `--self-test` 独立进程 500 次：`500/500` 成功；最大 `854.062 ms`；候选
  Release 残留进程 0。
- Rust 真实主窗 20 次正常关闭：`20/20` 成功，关闭 p95 `141.169 ms`。
- 主界面会按工作区反算可用布局缩放；`96/120/144 DPI` 在 `1024×768` 与
  `1920×1080` 工作区均有自动化边界测试，窗口跨屏后会重新夹紧位置。HUD 同步按 DPI
  缩放，保留灰/绿状态、目标摘要、计时、点击穿透和拖动保存位置。
- POE2 最多 8 行、三种 F10 启动热键、F11 框选、F12 停止/确认、HUD 显隐和选区保存
  已接到真实设置与运行时，不再是仅存在于界面上的占位行为。
- 截图测试与实时监控共享生产识别器；渐进识别允许在 3 轮以后继续，最多 128 轮后返回
  明确的“不收敛”故障，取消操作始终优先，不会弹出迟到结果。
- 红色告警每次显示都会重新查询虚拟桌面和目标显示器，并响应显示器拓扑/DPI 变化；只有
  在红窗可见、可点击且覆盖完整虚拟桌面之后，短时输入闸门才转交所有权。录屏亲和性设置
  失败只给出兼容性警告，不会阻止告警本身。

资源预检另使用生产 Runtime、WIC、WinRT 和 Paddle/ONNX 路径完成：60 秒未变化桌面
监控的平均整机 CPU 为 `0.0048%`，private bytes 只增加 `20,480 B`，handles
`220→216`；固定用户真实截图逐次重新识别 60 秒共 `630` 轮、OCR 累计 `34.554 s`，
平均整机 CPU 为 `1.7979%`，private bytes `70,451,200→71,618,560 B`
（增加 `1,167,360 B`，低于 5 MiB 门槛），handles `218→217`，threads
`11→13`。截图线程、WIC decoder 和同 profile ONNX recognizer 现在由一个容量为 1 的
常驻 worker 复用；每个截图请求仍清除临时识别证据，不能借上次结果空转通过。该 60 秒
测试是固定真实截图的生产 OCR 资源预检，不是 2 小时真实游戏门禁。

同一候选二进制随后执行 300 秒诊断，共 `3,157` 轮、OCR 累计 `172.785 s`。脚本原有的
首末单点算法得到 private bytes `74,481,664→83,013,632 B`（增加 `8,531,968 B`），
因此 JSON 仍如实记录为 **fail**；`-SkipThresholds` 只让脚本在写完证据后正常返回，
不会把失败改成通过。handles `220→217`、threads `11→8`，后 150 秒线性斜率约
`+0.382 MiB/min`，最后 90 秒的首/末 30 秒窗口均值为 `73.188→73.694 MiB`。
30 秒窗口均值依次为 `69.529、71.049、71.119、70.494、72.951、71.856、72.690、
73.110、72.521、73.775 MiB`，更符合原生分配器预热/高水位后在约 `72–74 MiB`
附近的平台，而不是句柄或线程随轮次线性累积。不过这只能辅助解释首末单点的相位敏感性；
它既不能覆盖原始门槛失败，也不能代替 2 小时真实游戏门禁。

可信证据为 `resource-soak/20260813-153727-screenshot-*`（60 秒）和
`resource-soak/20260813-153926-screenshot-*`（300 秒），二者的可执行文件 SHA-256 均为
`DF7FE34CBF70755F0B5E039B5408EE40CB3EAA915DF5463C41CB959EE92513DC`。更早的
`20260813-153154` 运行虽然通过资源阈值，但 `1,711` 轮只累计 `0.074 s` OCR，暴露了
跨独立截图请求复用临时指纹结果的诊断盲点；修复后才得到上述每轮约 `54.8 ms` 的真实
OCR 压力数据，因此该次空转结果不计入验收。

自动化必须按 PID 和窗口标题选择配置主窗。`Process.MainWindowHandle` 会优先返回状态
浮窗；向状态浮窗或无标题辅助窗发送 `WM_CLOSE` 得到的超时是假结果，不应据此修改产品
生命周期。

## 8. 正式切换前仍需完成

繁中五进程 A/B、全 Paddle 路径、高 DPI/行为对齐和告警拓扑修复均已完成，不再列为
待办；不过 POE2 p50 未达到快 10% 的理想门槛，当前性能结论仍只支持 Preview。剩余
必须取得的证据是：

1. 恢复 POE1 English 私有真实截图清单并跑五轮正例、语义近邻和跨截图反例。
2. 采集一张游戏原生 tooltip 中同一词缀自然换成两行的私有截图；生产 strict 预检确认
   `physical_line_count=2` 后，补跑六档瞬态回放。不得用 `.NET --wrap-case` 人工重排素材
   代替这项证据。
