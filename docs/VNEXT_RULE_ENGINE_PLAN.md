# POE Alarm 1.0：规则功能与后续规划

> 基准版本：`0.6.1`。1.0 在保留原有快速监控体验的基础上，增加多词缀组合和数值条件。

## 1. 1.0 的功能范围

1.0 只提供两个清晰入口：

| 功能 | 适合场景 | 停手条件 |
| --- | --- | --- |
| 快速单词缀 | 洗一条目标词缀、追求最快响应 | 指定完整词缀出现时报警；和旧版一样忽略数值大小 |
| 多词缀组合 | 一件装备有多种可接受结果，或需要限制数值 | 任一组结果成立时报警；每组可设置“至少命中几条” |

两种功能共用同一套词缀判断规则。多词缀组合只是表达能力更强，不会另写一套识别逻辑，也不会改变已经验证过的快速监控流程。

### 已移除：谨慎模式

谨慎模式曾尝试在每次制作操作之间暂停鼠标点击，但实机测试出现了启动监控后反复卡住、目标命中时仍未可靠拦截等问题。更重要的是，这项功能如何与玩家的完整制作流程配合还没有形成闭环。

因此，1.0 已完整移除谨慎模式及相关界面、黄色提示和点击拦截行为。旧版预览配置若曾选择谨慎模式，升级后会自动回到快速监控，不影响原有目标词缀和多词缀规则。

未来只有在使用流程、停止条件和失效时的处理方式都重新设计清楚，并通过足够的实机验证后，才会重新讨论类似功能。目前不承诺实现时间，也不把它列为 1.0 的能力。

## 2. 规则如何判断

### 2.1 数值条件

快速单词缀沿用旧版行为，只判断完整词缀文字并忽略具体数值。在多词缀组合中，用户可以为词缀里的一个或多个数值分别设置：

- 不限制；
- 至少为某个值；
- 至多为某个值；
- 位于某个闭区间；
- 精确等于某个值。

例如：

```text
原文：179% increased Physical Damage
模板：<数值>% increased Physical Damage
实际值：179
```

像 `Adds X to Y` 这样包含两个数值的词缀，会分别检查两个位置。缺少数值、百分号不一致或数值位置数量不一致时，都不会误判为命中。

程序比较的是装备提示框中实际显示的值。品质、催化剂或特殊效果可能改变显示值，程序不会反推出未经加成的基础值或词缀等级。

### 2.2 多种可接受结果

一套规则可以包含多组“可接受结果”：

```text
停手规则
  └─ 可接受结果（可添加多组，命中任意一组即可）
       ├─ 至少命中 N 条
       └─ 词缀条件（完整词缀文字 + 可选数值条件）
```

- 多组结果之间是“任选其一”。
- 每组可设置“任意一条”“至少 N 条”或“全部命中”。
- 同一条实际词缀在一组结果中最多计算一次，不能靠文字重叠重复凑数。
- 不提供任意层级的复杂逻辑嵌套，避免规则难以理解。
- 首版最多保存 8 组可接受结果、总计 32 条词缀条件；超过上限时会在保存前提示。

原有单词缀判断采用严格的完整词缀匹配，并不是只搜索某个关键词。因此，“法术暴击率”不会被当成“全域暴击率”。多词缀组合继续沿用这一原则，并额外验证同一条词缀不会被重复计数。

### 2.3 判断结果和说明

规则判断只产生两种最终结果：命中或未命中。

- 命中时，记录是哪一组结果成立、对应哪些实际词缀以及数值是否合格。
- 未命中时，能够区分文字不符、数值不符或命中数量不足。

识别结果不清楚时，不会把模糊文字当作确定命中。识别或鼠标监听发生异常时，程序应结束本轮监控、给出明确提示，并确保不影响系统正常输入。

## 3. 1.0 暂不处理的场景

- 记录开工前的装备，并只计算后来新增的词缀。
- 要求原有词缀一直存在，或在它消失时报警。
- 读取按住 Alt 后显示的词缀等级、前缀、后缀和词缀类别。
- 把分两行显示的复合词缀拆成多个独立词缀。
- 自动换算品质、催化剂或特殊效果对数值的影响。
- 根据词缀数量动态寻找装备提示框边界。
- 依靠文字颜色判断破裂、工艺、隐式或附魔来源。
- 联网查询词缀数据库、自动点击或替玩家决定下一步制作操作。

### 为什么“只计算新增词缀”不是多词缀组合

这两项功能回答的问题不同：

- 多词缀组合判断：当前画面中的哪些词缀组合值得停手？
- 开工前后对比判断：符合条件的词缀是原本就有，还是本轮新出现？原有词缀是否还在？

例如，珠宝开工前已有“暴击伤害”，规则要求“暴击伤害 + 法术暴击率”。当前的多词缀组合会让旧的暴击伤害参与计数；“只计算新增”则必须排除它。

普通装备提示框又不能可靠说明词缀来源。若基础记录漏掉了颜色不同的破裂词缀，程序就无法证明它原本存在或后来消失。与其提供会带来错误安全感的半成品，1.0 选择不实现这项功能。

## 4. 代码边界

### 核心规则

```text
Matching/                         # 原有严格完整词缀判断
Rules/Models/                     # 停手规则、结果组、词缀条件、数值条件
Rules/Parsing/                    # 从文字中提取模板和实际数值
Rules/Compilation/                # 开始监控前检查并准备规则
Rules/Evaluation/                 # 判断命中结果并防止重复计数
```

核心规则不依赖界面、截屏、文字识别、鼠标监听或设置存储。原有单词缀匹配继续作为快速监控的兼容基础；多词缀组合必须保持相同的严格文字语义。

### 程序功能

```text
Recognition/                      # 把选区画面识别成词缀文字和数值
Monitoring/                       # 复用 0.6.1 已验证的快速监控流程
Configuration/                    # 保存规则并兼容旧设置
RulesUi/                          # 单词缀和多词缀规则界面
Replay/                           # 用固定识别结果复查规则和耗时
```

识别层只负责提供画面里看到了什么；规则层负责判断是否达到停手条件；告警层只接收最终结果。各层不重复实现同一套词缀逻辑。

## 5. 设置兼容

- 保留旧版每个游戏的目标词缀、选区和识别语言。
- 从 0.6.1 升级时默认进入快速单词缀，不会自动开启数值限制。
- POE1 与 POE2 的规则、选区和识别语言继续分开保存。
- 非法的多词缀规则会指出具体问题并阻止启动，不会静默删除用户配置。
- 遇到比当前程序更新的设置格式时，只使用内存中的安全默认值，不覆盖原文件。
- 旧版预览中的谨慎模式设置只会降级为快速监控，不再恢复任何点击拦截行为。

## 6. 性能要求

所有对比都使用同一台机器、相同截图和选区，并把首次启动与稳定运行分开记录。

- 画面没有变化时继续使用快速预检，不启动文字识别。
- 快速监控的画面变化判断以约 30 毫秒为目标，不接受秒级停顿。
- 常见装备提示框在最多 32 条条件下，纯规则判断的 95% 耗时不超过 1 毫秒。
- 极端重复词缀测试必须有防卡死上限，不能因为组合计算出现指数级等待。
- 规则只在开始监控时准备一次，不在每帧重复创建正则表达式或重新整理目标词缀。
- 优化多词缀功能时，不修改 0.6.1 已验证的识别阈值和快速监控流程来换取速度。

## 7. 交付阶段

### 已完成：固定 0.6.1 基线

- 保存核心匹配、真实截图、输入保护和界面的回归结果。
- 为快速监控建立可重复的性能对照。

### 已完成：多词缀规则核心

- 完成数值提取、数值条件、可接受结果、一对一计数和规则检查。
- 用原有单词缀案例证明严格匹配语义没有改变。

### 已完成：设置和界面接入

- 保留旧版单目标设置，加入多词缀组合编辑和分游戏保存。
- 截图测试与固定回放使用同一套规则判断流程。
- 快速单词缀路径不受批量识别实现影响。

### 1.0 发布门槛

- 快速单词缀和多词缀组合都通过功能、误报、漏报、关闭程序和性能回归。
- 中文小数、数值边界和多种可接受结果通过真实截图验证。
- 不包含任何尚未通过实机验证的点击拦截功能。

## 8. 验收清单

### 规则正确性

- 原有单词缀判断的全部正反例原样通过。
- 覆盖区间边界、最小值、最大值、精确值、小数、负数、百分比、双数值、缺少数值和单位冲突。
- 多组结果能正确“任选其一”；组内“任意一条”“至少 N 条”和“全部命中”正确。
- 一条实际词缀不能满足同一结果中的两个条件；两条不同词缀可以分别贡献一次。
- 文字严格命中但数值不合格时不报警。

### 兼容性

- 使用真实 0.6.1 设置升级后，目标、选区、语言和游戏隔离不丢失，数值仍默认不限制。
- 快速监控在已有英文、繁中、POE1、POE2 语料和截图上的正例数量不下降，既有负例误报仍为零。
- 快速监控的启动、停止、命中确认、尾击吸收和全局热键行为不变。
- 关闭程序时能够取消正在进行的截图识别和设置保存，不出现卡死。

### 性能与说明

- 常见装备提示框满载 32 条条件时仍满足纯规则判断的毫秒级预算。
- 报警详情能指出触发的结果、对应实际词缀和每个数值条件。
- 固定回放能说明未命中的原因，并记录截屏、文字识别、规则判断和总耗时。

1.0 的原则很明确：保住已经验证的快速能力，只发布实机可用、逻辑闭环的功能。
