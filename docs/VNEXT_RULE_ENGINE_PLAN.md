# POE Alarm vNext：规则引擎与安全监控计划

> 基准：`0.6.1`。本计划只在该正式版本之上演进，不把本地旧提交带入新架构。

## 1. 产品定案

界面给用户三个清晰入口，但内部不实现三套互相复制的业务逻辑：

| 界面入口 | `RuleSet`（停手条件） | `MonitoringPolicy`（何时允许下一次操作） |
| --- | --- | --- |
| 快速模式 | 单个词缀，默认忽略数值；保持 0.6.1 的使用方式 | `Fast`，保持 0.6.1 的监控、缓存与闸门行为 |
| 多词缀命中模式 | 多个“可接受结果”；任一结果成立即报警 | `Fast` |
| Mirror Tier 安全模式 | 可使用同一套单词缀或多词缀规则，通常启用数值约束 | `Guarded`，每个变化状态判定完成前不允许洗到下一轮 |

因此内部产品模型是正交的：

```text
ModePreset（只属于 UI）
  ├─ RuleSet：什么结果值得停手
  └─ MonitoringPolicy：什么时候可以放行下一次点击
```

“Mirror Tier”不是另一套词缀语义，也不复制多词缀编辑器。以后即使增加新的保护策略，也不会把规则组合、OCR 和鼠标状态机揉在一起。

## 2. 规则语义

### 2.1 数值槽约束

0.6.1 的 `AffixCanonicalizer` / `FullLineAffixMatcher` 会保留 `<NUM>`、`<PCT>`、正负类型，但故意丢弃数值大小。快速模式必须继续支持这一语义。

vNext 在旁路增加结构化解析结果，不修改旧归一化结果：

```text
原文：179% increased Physical Damage
模板：<PCT0> increased physical damage
数值：slot 0 = 179
```

每个槽支持：

- `Ignore`：忽略数值，等同 0.6.1；
- `BetweenInclusive(min, max)`：闭区间；
- `AtLeast(min)`；
- `AtMost(max)`；
- `Exact(value)`。

多个数值各自约束，例如 `Adds X to Y` 分别得到 slot 0、slot 1。整数、小数、百分比与正负结构必须保留；缺数、单位冲突或槽位数量不一致不能当作命中。粘贴 PoEDB 范围时可以把范围作为编辑建议，但本阶段不接词缀数据库，也不把范围推断成 Tier。

### 2.2 可接受结果

```text
RuleSet
  └─ AcceptableResult[]                 # 结果之间为 OR
       ├─ RequiredCount                 # 至少命中 N 条
       └─ AffixCondition[]              # 完整词缀 + 可选数值槽约束
```

- 任一 `AcceptableResult` 成立即报警。
- `任意一条` 是 `RequiredCount = 1`；`全部命中` 是 `RequiredCount = 条件数`，无需另造布尔表达式语言。
- 每个结果内，一条实际 modifier 最多贡献一次命中。条件与实际 modifier 使用一对一分配，不能让同一行同时凑出“两条命中”。
- 不做任意深度的 AND/OR 嵌套。
- 首版限制最多 8 个可接受结果、总计 32 个条件；超限在编辑阶段拒绝，避免不可读配置和无界开销。

0.6.1 已经是严格整句匹配，并非 substring matcher，所以“法术暴击率”被当成“全域暴击率”的典型关键词误命中，在旧单词缀路径中已有防护。多词缀引擎仍必须新增一对一分配测试，因为计数规则引入了旧版本没有的重复占用风险。

### 2.3 判定结果

M1 规则引擎输出 `Match / NoMatch` 加逐组、逐条件、逐数值槽证据，而不是只返回一个不可解释的 `bool`：

- `NoMatch`：没有可接受结果成立；证据仍指出是文字未命中、数值不合格，还是一对一占用不足；
- `Match`：指出触发的结果、条件、实际行和每个数值槽。

`Uncertain` 属于 M4 `Guarded` 监控策略的决策层，而不是让纯文字规则凭空猜 OCR 置信度：候选模板相关的数字缺失、连续稳定读数冲突或识别器明确给出的低置信证据会进入黄色人工检查并保持本轮保护。`Fast` 策略不得把这些证据伪装成确定命中。OCR/钩子故障仍沿用 0.6.1 的 fail-open 原则：停止本轮、明确警告并释放系统输入，不能无限锁住桌面。

## 3. 范围

### 现在：vNext 第一条可发布链路

- 冻结并持续回归 0.6.1 快速模式。
- 加入版本化 `RuleSet`、数值槽约束、可接受结果与一对一计数。
- 快速模式无额外配置步骤；多词缀模式使用折叠式“可接受结果”编辑器。
- 规则在开始监控时一次性编译；每帧只处理 OCR observation 和预编译规则。
- POE1 / POE2 分别保存规则，继续沿用各自的选区和 OCR 语言。
- 截图测试与 Replay 输出命中原因、实际值、失败约束和耗时。
- 数值约束开启时显示 Catalyst/品质/特殊效果警告：程序比较的是 tooltip 显示值，不保证它等于未加成的原生 Tier 数值。

### 下一步：Mirror Tier 安全监控

- 新增独立的 `Guarded` 监控策略：检测到语义画面变化后，先让已经交给游戏的当前按键完整释放，再阻挡下一次按下，直到该状态得到 `Match`、`NoMatch` 或 `Uncertain`。
- 启动监控前预热本策略需要的 OCR/数字复核资源，避免第一次变化时懒加载。
- 不增加固定的两秒等待；仅在 recognizer 明确要求渐进重扫或数字复核时继续持有保护。
- `Match` 进入现有红色锁定告警；`Uncertain` 进入黄色人工检查；`NoMatch` 立即放行。
- 安全策略及其可选数字复核器独立于快速路径，不能改动快速路径已验证的 OCR 阈值、缓存判断或鼠标状态转换。

### 延后，不在当前版本实现

- **基准装备 / 只计算新增词缀 / 已有词缀必须存在 / 消失报警。**
- Alt 高级描述、Tier、Prefix/Suffix、mod family 与空前后缀统计。
- Hybrid 词缀和合并显示的拆分判断。
- 自动补偿 Catalyst、品质或特殊效果；当前只提示风险。
- 自动定位 tooltip 黑色矩形、动态 ROI 和按颜色裁出正文。现有大致选区在实测中可用，tooltip 边界随词缀增减而变化，本阶段不为此改写捕获链路。
- 破裂、工艺、隐式、附魔等来源分类；POE1/POE2 的颜色规则不强行共用。
- 完整词缀数据库、联网 PoEDB、任意脚本、自动点击以及额外做装决策场景。

#### 为什么“只计算新增词缀”不等于“可接受结果组”

两者回答不同问题：

- 可接受结果组回答：**当前观察到的哪些词缀组合值得停手？**
- 基准差分回答：**一条满足条件的词缀是开工前就存在，还是本轮新出现；原有词缀是否仍然存在？**

例如基准珠宝已有“暴击伤害”，结果组要求“暴击伤害 + 法术暴击率”。只看当前 tooltip 时旧暴击伤害可以参与计数；“只计算新增”则必须排除它。这不是重复功能。

但当前生产 OCR 以蓝色词缀为核心证据，金色破裂词可能不进入同一 observation 集。此时捕获基准会漏掉破裂词，后续既不能可靠判断它是旧词，也不能证明它仍存在。半成品基准功能会制造虚假的安全感，因此延后到非 Alt 状态下也能稳定覆盖蓝色与金色行、且分别通过 POE1/POE2 截图回归之后再做。未来实现也不能要求用户在连点时长按 Alt。

## 4. 模块边界

### `PoeAlarm.Core`

```text
Matching/                         # 0.6.1 严格整句能力，保留兼容
Rules/Models/                     # RuleSet、Result、Condition、NumericConstraint
Rules/Parsing/                    # 结构化模板与实际数值槽
Rules/Compilation/                # 启动时编译、校验上限
Rules/Evaluation/                 # 纯函数判定与一对一分配
```

- Core 不引用 WPF、截屏、OCR、鼠标钩子或设置存储。
- `FullLineAffixMatcher` 继续作为快速单规则兼容实现；新规则匹配必须复用其严格语义或通过等价性测试，不能退化为关键词匹配。
- `ModifierObservation` 带稳定的物理/逻辑行身份、规范化文本、数值槽和可选证据；规则引擎不读取位图。

### `PoeAlarm.App`

```text
Recognition/                      # 现有 recognizer；负责像素到 observation
Recognition/Safe/                 # 仅 Guarded 可用的数字复核（如确有需要）
Monitoring/Fast/                  # 0.6.1 行为的快速策略
Monitoring/Safe/                  # 独立的 Mirror Tier 状态机
Configuration/                    # versioned RuleSet DTO 与迁移
RulesUi/                          # 三个入口和高级结果编辑器
Replay/                           # 同一 observation -> rule evaluation 管线
```

识别层可以接收预编译目标作为“候选提示”，但不能自行决定 `至少 N 条` 或报警。监控策略只能管理捕获节奏、输入保护和三态结果；它不能实现词缀语义。告警层只消费最终 decision。这样安全模式即使采用额外数字复核，也不会污染快速 OCR。

## 5. 兼容与迁移

- 设置增加显式 `SchemaVersion`、每游戏可选的 `StructuredRuleSet` 与独立的 `MonitoringPolicyId`；继续保留 `GameProfileSettings.TargetAffix`，不破坏 0.6.1 单目标与降级读取。当前策略枚举只开放已验证的 `Fast`；M4 真正实现安全状态机后才加入 `Guarded`，避免配置文件提前承诺不存在的保护能力。
- 读取 0.6.1 设置时，保留每个游戏的 `TargetAffix` 并明确选择 `Quick`；需要进入结构化引擎时，适配器才把它编译成一个结果、一个条件、`RequiredCount = 1`、所有数值槽 `Ignore`。旧设置不会被静默改写成高级模式。
- 迁移绝不根据粘贴文本自动开启范围或 Tier 判断，否则旧用户会从“忽略数值”无声变成“限定数值”。
- `Fast` 必须保留 0.6.1 的实际保护矩阵：POE1 English 不新增预判闸门；POE2 与繁中继续使用已有 changed-frame 短时闸门。
- 缺失或未知的新字段使用兼容默认值；非法高级规则阻止启动并指出具体路径，不静默删规则。
- 若磁盘设置的 `SchemaVersion` 高于当前程序支持版本，当前程序只使用安全的内存默认值，并把原文件保持只读、逐字节不改；不能把未来 schema 归一化后覆盖成旧版本。
- 设置仍按 POE1 / POE2 隔离，切换游戏不会串用规则、选区或 OCR 语言。

## 6. 性能硬指标

所有指标以同一台机器、Release x64、相同截图/选区和 warm OCR 对比 0.6.1；冷启动单独记录，不混入 steady-state。

- 未变化帧继续走 fingerprint/cache，不因规则数量触发 OCR；其预检 p95 不高于 0.6.1 基线 + 1 ms。
- 快速模式 changed-frame 的 p50 不高于 0.6.1 基线 + 3 ms，p95 不高于基线 + 5 ms；目标仍为 p50 约 30 ms，不接受秒级判定。
- 常规 tooltip（最多 32 个条件、约 6–8 条实际 modifier）的纯规则判定 p95 ≤ 1 ms；32 条同模板密集候选另设 ≤ 100 ms 的防退化门禁，防止一对一分配出现指数级卡死；开始监控时的规则编译 ≤ 10 ms。
- 规则编译、正则构造和目标规范化不得发生在逐帧热路径；OCR 模型/会话跨帧复用。
- `Guarded` 在启动前完成资源预热；warm capture-to-decision p95 目标 ≤ 80 ms。需要重扫时必须记录次数和原因，不能靠固定长延时换准确率。
- 性能不达标时先优化结构化解析与批量匹配，不修改 0.6.1 快速 OCR 阈值来“换速度”。

## 7. 分阶段里程碑

### M0：固定 0.6.1 基线

- 保存现有 Core、POE2 corpus、真实截图 manifest、输入闸门和 UI snapshot 的结果与延迟。
- 为快速路径建立可重复的 p50/p95 对照命令。

### M1：纯 Core 规则引擎（不接 UI）

- 完成结构化数值槽、约束、结果组、编译和一对一求值。
- 用现有 `FullLineAffixMatcher` 回归证明旧语义未变。

### M2：兼容适配与设置

- 将单目标适配为 `RuleSet`，增加 schema 迁移与 POE1/POE2 独立保存。
- 快速模式先经过完整回归，再开放新规则接入。

### M3：多词缀与数值 UI

- 交付三个入口、折叠式可接受结果编辑器、数值槽编辑、验证提示和可解释诊断。
- 截图测试与 Replay 使用同一编译/求值链路。
- 当前开发预览已开放 POE1 English 的单次严格批量 OCR，并为 POE2 English 保留 changed-frame 的双 Windows 引擎确认；POE2 的多目标局部 Paddle 辅助仍未启用。繁中与无 Windows 中文能力时的 Paddle 路径在共享候选/物理行证据完成前明确拒绝结构化监控，不允许静默退化为 target-free OCR。快速单目标路径不受此门禁影响。

### M4：Guarded 安全策略

- 单独实现并测试 Mirror Tier 状态机、预热、黄色不确定暂停与故障释放。
- 不通过安全验收时不以“Mirror Tier”名义发布；快速和多词缀模式不被阻塞。

### M5：实战回放与发布门禁

- 收集不同 UI 缩放、选区和点击节奏的真实制作序列。
- 只有功能、误报/漏报、输入安全和性能门禁全部通过，才替代 0.6.1 为默认正式版本。

## 8. 验收清单

### 规则正确性

- 0.6.1 的全部 matcher 正反例原样通过。
- 覆盖区间边界、最小/最大/精确、小数、负数、百分比、双数值槽、缺槽和单位冲突。
- 多个结果为 OR；组内 `1/N`、`N/N`、任意 N 正确。
- 一条 observation 在同一结果内不能满足两个条件；两个不同 observation 可以分别满足。
- 文字严格命中但数值不合格时不报警；数字证据冲突得到 `Uncertain`，不能误判为 `Match`。

### 兼容性

- 用真实 0.6.1 `settings.json` fixture 升级后，目标、选区、语言和游戏隔离不丢失，数值仍为 Ignore。
- 快速模式在现有 English/繁中、POE1/POE2 corpus 与截图 manifest 上，正例数量不下降、既有负例误报仍为 0。
- 快速模式的启动、停止、命中确认、300 ms 尾击吸收和全局热键行为不变。

### 安全策略

- 变化发生于按键已按下时，先放行该次配对的 MouseUp；下一次 MouseDown 才被保护。
- `NoMatch` 后立即成对放行；`Match` 保持红色锁定；`Uncertain` 保持黄色人工检查。
- 连续变化、渐进重扫和快速连点 Replay 中，每个可能目标状态都在下一次有效点击前得到判定。
- 手动停止、异常、关闭、钩子失效和 watchdog 均释放输入并停止本轮，不留孤立按键状态。

### 性能与可解释性

- 常规 tooltip 满载 32 条条件仍满足第 6 节 1 ms 预算；32×31 同模板密集反例满足防卡死门禁。
- 报警详情能指出：触发结果、对应实际行、模板判断、每个槽的实际值与约束。
- 未命中/不确定 Replay 能说明失败原因，并记录 capture、OCR、规则求值和总耗时。

以上门禁的核心原则是：先保住 0.6.1 已验证的纯粹快速能力，再通过独立模块增加表达力和保护强度。
